# KAIRO PRODUCT EXPERIENCE BLUEPRINT
## The Operating System for a Student's UTME Journey

*(Builds on everything already designed — the Learning Engine, Student Intelligence Model,
Question Intelligence Model, Subject Knowledge Graph, Daily Decision Engine, and Home Dashboard.
Does not redesign any of them. This document reorganises how students *access* that
intelligence, around intent rather than a single forced path.)*

---

## 0. THE PHILOSOPHY SHIFT

KAIRO is not a learning app and not a CBT app. It is the **operating system for a student's
entire UTME preparation journey.** A student does not arrive with one intention every day —
some days they want to practise, some days they want to simulate the real exam, some days they
want a quick competitive hit, some days they want to fix yesterday's mistakes, some days they
just want one concept explained.

Forcing all of these into a single "learning path" is the same decision-fatigue failure the
Daily Decision Engine was built to eliminate at the session level — except here it would happen
at the *app* level instead. The fix is the same principle applied one layer up: **organise the
product around intent, not around a single workflow.**

Every section below is a different *front door* into the same Intelligence Engine. The student
experiences them as distinct destinations. Internally, none of them are silos — every action in
any section updates the same underlying Student Intelligence Model, and every recommendation
anywhere in the app is still generated by the same Learning Engine, Subject Knowledge Graph, and
Daily Decision Engine already specified.

---

## 1. UPDATED CORE NAVIGATION

**Home · Practice · CBT Exam Mode · Challenges · Learn · Review · Insights · Profile**

Eight destinations is more than the five-item navigation ceiling set in the Home Dashboard spec
(Home Dashboard §9). This is resolved by treating navigation as two tiers:

- **Persistent bottom navigation (5 max):** Home, Practice, CBT Exam Mode, Review, Insights —
  the five a student reaches for most often and under the most time pressure.
- **Reachable from Home / a secondary tab:** Challenges, Learn, Profile — each has a strong
  entry point from Home (a Challenge card, a "Learn this" link from an explanation, a profile
  icon) so nothing is more than one extra tap away, without permanently occupying primary chrome.

This keeps the dashboard's "one tap to start studying" requirement intact while giving every
intent its own credible home.

## 2. PRACTICE

### Purpose
Daily intelligent practice — the direct student-facing surface of the Recommendation Engine
(Learning Engine §4) and the Daily Decision Engine's Today's Mission (DDE §4–5). This is where
most session time lives, and it is what Today's Mission on Home routes into by default.

### Student journey
Open Practice (directly, or via "Start Mission" on Home) → land inside a live session, no
subject-picker gate → answer questions → receive immediate, tagged feedback → session adapts in
real time (DDE §6–7) → session closes on a Confidence Builder → Reflection screen.

### Major screens
- **Practice Home** (subject/topic quick-filter, optional — never mandatory before starting)
- **Live Question Screen** (stem, options, flag/bookmark, progress indicator)
- **Immediate Feedback Screen** (correct/incorrect framing per Kai's tone rules, Learning
  Engine Phase 2 §7.2)
- **Session Reflection Screen** (Mission Generator's closing artifact, DDE §4.2)

### User interactions
Answer selection, flag-for-review, request explanation, request a different framing of the same
concept ("explain this another way"), pause/resume (feeds Quick Resume on Home), end session
early (never penalized — Confidence Builder is guaranteed to run first if possible).

### Data flow
Every attempt → Learning Engine's question-level loop (Phase 1 §4.2) → updates Concept Node
state, Academic Profile, Behaviour Profile → feeds Elite/KAIRO Score → feeds Review's mistake
and Fading queues → feeds Insights.

### Intelligence Engine interactions
Full DDE session-planning and live-adaptation logic (DDE §3, §6, §7) applies unmodified —
Practice *is* the DDE's primary execution surface.

### Edge cases
Student opens Practice with zero prior data → Orienting diagnostic pass (Learning Engine §11).
Student abandons mid-session → state preserved exactly, offered as Quick Resume, never
discarded (DDE §8). Sparse question pool for a topic → honestly signals "more coming soon"
rather than recycling (Learning Engine §11).

### Future scalability
Subject/topic quick-filters can expand to Post-UTME and other exam types without structural
change, since the Recommendation Engine is already exam-type-scoped (Learning Engine §12,
Subject Knowledge Graph §12).

## 3. CBT EXAM MODE

### Purpose
Replicate the real JAMB CBT experience as faithfully as possible — this is the single biggest
reason many students currently install separate CBT-simulation apps, and KAIRO must not
concede that need to a competitor. Unlike a standalone CBT app, every attempt here still feeds
the same Intelligence Engine everything else does.

### Student journey
Choose CBT Exam Mode → select subject combination and mode (full mock / single-subject
practice exam) → authentic pre-exam instructions screen (mirrors real JAMB flow, builds
familiarity and reduces exam-day anxiety) → timed exam interface → submit (manually or
auto-submit on time-up) → detailed performance report → insights routed back into the
Intelligence Engine.

### Major screens
- **CBT Setup Screen** (subject combination, mode, duration)
- **Pre-Exam Instructions Screen** (JAMB-authentic framing — deliberately, since familiarity
  with the real interface is part of the value)
- **Exam Interface** (question navigator grid, flag question, timer, submit)
- **Submission Confirmation Screen** (explicit, deliberate — no accidental submits)
- **Performance Report Screen** (score by subject, time-per-question analysis, flagged-question
  review, comparison against the student's own target score from Section 1 of the Student
  Intelligence Model)

### User interactions
Navigate freely between questions (unlike Practice's linear flow), flag for review, jump via
the question grid, submit early or let the timer expire, review answers after submission
(explanations unlock only post-submission, to preserve exam authenticity during the attempt).

### Data flow
Full attempt log → Question Intelligence Model (calculation load, timing, misconception
tagging) → Learning Engine's Concept Node updates, weighted for exam-condition performance →
Subject Knowledge Graph gap detection (a subject-wide weak pattern surfaces here faster than in
isolated Practice, because CBT forces breadth in one sitting) → Insights and Review both update
immediately after submission.

### Intelligence Engine interactions
CBT Mode does not bypass the engine — it's a different *data collection context* for the same
model. Response-time baselining (Learning Engine §1.3) gets its most reliable signal here,
since conditions are standardized and timed. Post-exam, the DDE treats a completed mock as a
strong trigger for re-planning the next several days' Practice priorities.

### Edge cases
Connectivity drop mid-exam → local state preserved, exam resumes from the same point on
reconnect, timer behavior clearly communicated (never silently penalizes for a network gap).
Student exits without submitting → treated as an incomplete attempt, not scored, but partial
data (if substantial) can still inform Behaviour Profile fatigue signals.

### Future scalability
Mode structure generalizes directly to Post-UTME CBTs and institution-specific exam formats —
new subject combinations and timing rules, not a new architecture.

## 4. CHALLENGES

### Purpose
An independent, admin-curated competitive layer that replaces the need for external quiz
platforms (e.g., Quizbot) and functions as KAIRO's primary organic growth and acquisition
channel — a student can receive a shareable WhatsApp link, complete a Challenge with zero
onboarding friction, and discover the rest of KAIRO afterward.

### Student journey
Receive a shared link or open Challenges from Home → land directly on a specific Challenge
(no account required for the attempt itself, though completion/leaderboard participation may
prompt sign-up) → attempt within the availability window → see results and leaderboard
placement immediately → soft, non-pushy invitation into the full KAIRO experience.

### Major screens
- **Challenge Landing Screen** (title, cover image, description, difficulty, question count,
  timer if applicable — a self-contained, shareable moment)
- **Challenge Attempt Screen** (deliberately simpler UI than CBT Mode — this is meant to feel
  fast and low-stakes)
- **Challenge Results Screen** (score, leaderboard position, share-your-result prompt)
- **Challenges Hub** (browse active/upcoming challenges, past results, for signed-in students)

### User interactions
Attempt, share result, view leaderboard (opt-in visibility per the Motivation Engine's
cohort-based principle, Learning Engine Phase 2 §8.4), tap through into KAIRO proper after
completion.

### Data flow
A Challenge attempt from a non-account visitor is held as anonymous session data until/unless
they convert to a full account, at which point it merges into their Student Intelligence Model
as historical signal (not discarded, per the platform's append-only attempt-history principle,
Student Intelligence Model §2). For existing students, Challenge attempts feed Insights and
contribute lightly to Consistency (Elite/KAIRO Score §6.2) without being allowed to distort
Retention, since Challenges are format-optimized for fun and speed, not spaced-recall integrity.

### Intelligence Engine interactions
Challenges are administrator-authored (only TECHMED admins create them — never students), so
they sit outside the Recommendation Engine's automatic selection logic. However, a completed
Challenge's error patterns still flow into the same misconception/tagging pipeline (Question
Intelligence Model §4) as any other attempt, so even a "fun" Challenge quietly improves the
Knowledge Model.

### Edge cases
Non-account participant wants their leaderboard position preserved after signing up → account
creation flow explicitly offers to link the anonymous attempt. Challenge availability window
closes mid-attempt → student is allowed to finish an already-started attempt even if the window
technically lapses seconds later; new attempts after close are blocked with clear messaging,
never silently discarded ambiguity.

### Future scalability
Sponsor-branded challenges, scholarship-qualifier challenges, and themed campaign weeks
(Section 4's "Biology Week," "Physics Weekend") all attach to the same Challenge object model —
new metadata (sponsor, prize, eligibility), not new architecture.

## 5. LEARN

### Purpose
Concept explanation, driven by practice rather than standing in for classroom teaching. KAIRO
does not aim to become an online school — Learn exists to answer "why did I get this wrong, and
what do I actually need to understand," anchored to a real question moment, not a syllabus of
video lessons.

### Student journey
Question → answer → explanation → concept summary → common mistakes → related questions →
mastery reinforcement. A student can also intentionally jump into Learn from Review or Insights
("explain this weak concept") rather than only arriving via a missed question.

### Major screens
- **Explanation Screen** (Question Intelligence Model §9's full structure: correct reasoning,
  why each wrong option is wrong, common mistake, exam tip, memory anchor, related concept,
  suggested follow-up, Kai's encouragement)
- **Concept Summary Screen** (the Learning Objective and plain-language description from the
  Subject Knowledge Graph §3.1, reachable when a student wants the concept on its own, not
  tied to one specific question)
- **Related Questions Carousel** (pulled from the Question Intelligence Model's relationship
  graph — Reinforcement, Extension, Alternative Representation, §6.2)

### User interactions
Read explanation, request an alternative framing (different analogy, per Kai's tone rule 1 on
never repeating a failed explanation verbatim), attempt a related question directly from the
explanation screen, bookmark a concept for Review.

### Data flow
Explanation views and re-explanation requests are themselves a signal — repeated requests for
the same concept feed the Plateau-detection logic (Learning Engine §11) even before a Fading
state technically triggers it.

### Intelligence Engine interactions
Learn is the direct output-facing layer of the Question Intelligence Model's Explanation
Intelligence (QIM §9). It does not run its own separate logic — it renders what the Learning
Engine and QIM have already computed about *why* a student got something wrong.

### Edge cases
Question has an incomplete explanation (QA gate not yet fully satisfied, QIM §11) → the
question does not enter live rotation in the first place, so this should not surface to a
student; if it does (legacy content), a fallback generic-but-honest explanation renders rather
than a broken screen.

### Future scalability
QIM §9.3 already notes the explanation structure is medium-agnostic — voice or short video
explanations can render from the same underlying content components without a new data model.

## 6. REVIEW

### Purpose
Where students return to consolidate — mistakes, bookmarks, weak topics, spaced repetition, and
forgotten concepts, all surfaced automatically. This is the direct student-facing home of
Memory & Revision Scheduling (Learning Engine Phase 2 §5) and the Subject Knowledge Graph's
Revision Paths (§9).

### Student journey
Open Review → see a prioritized, plain-language list ("3 things are fading," "2 mistakes from
this week") → tap into a focused Review session (interleaved, per §5.3, never a giant blocked
drill) → session behaves like Practice but is explicitly scoped to revision content.

### Major screens
- **Review Home** (categorized: Mistakes, Bookmarks, Fading Concepts, Weak Topics — each a
  distinct query over the same underlying data, Subject Knowledge Graph §9)
- **Review Session Screen** (same mechanics as Practice, scoped input)
- **Review Summary Screen** (what got Reinforced this session — the single most rewarding
  moment in Review, deliberately highlighted)

### User interactions
Select a review category, start a scoped session, bookmark/unbookmark, dismiss a suggested
review item (rare, logged as a signal rather than silently honored — a repeatedly dismissed
item may indicate a Hidden or Repeated gap worth escalating differently, Subject Knowledge
Graph §8.2).

### Data flow
Fully bidirectional with Practice and CBT Mode — every attempt anywhere in the app can populate
Review's queues; every Review session updates the same Concept Node states everything else
reads from.

### Intelligence Engine interactions
Review is the most direct expression of the Memory Scheduling engine (Learning Engine Phase 2
§5) and the Subject Knowledge Graph's seven Revision Paths (§9) — Quick, Deep, Confidence
Rebuilding, Exam Sprint, Recovery, Weak-topic, and Forgotten-concept review are all literally
selectable entry points here, translated into plain student-facing category names.

### Edge cases
Empty Review (nothing currently due) → this is a genuinely good state and should read as one
("You're caught up — nothing urgent right now"), never as a broken or empty-feeling screen.
Very large Fading queue after a long gap → Deep Revision path automatically favored over Quick,
and Recovery framing (DDE §8) applies if the gap crosses the At Risk threshold.

### Future scalability
The same category structure extends cleanly to Post-UTME/repeat-candidate multi-year knowledge
retention (Learning Engine §12) without new screens.

## 7. INSIGHTS

### Purpose
All analytics, consolidated — the KAIRO Score, accuracy, speed, consistency, streak, subject
and topic mastery, weekly/monthly reports, achievements. This is the analytics page the Home
Dashboard deliberately is *not* (Home Dashboard §2) — Insights is where a student goes when they
actively want the deeper picture, not where they're greeted by default.

### Student journey
Open Insights (from nav, or tap-through from a Home Dashboard strip) → see the KAIRO Score
front and center with a plain-language breakdown → drill into subject/topic mastery, trends,
and reports as desired.

### Major screens
- **Insights Home** (KAIRO Score badge + breakdown, headline trend line, quick links to Weekly/
  Monthly Reflection)
- **Subject/Topic Mastery Screen** (Subject Health, expanded from the Home Dashboard's
  compressed strip, Home Dashboard §4.11)
- **Weekly Reflection** (Learning Engine Phase 2 §8.2 — private, non-comparative)
- **Monthly Reflection / "KAIRO Wrapped"** (Learning Engine Phase 2 §8.3 — shareable, brand-
  reinforcing, Navy/Gold/Ibex visual identity)
- **Achievements Screen** (Recent Achievements expanded into a full, honest history)

### User interactions
Tap into any metric for its plain-language explanation (KAIRO Score §7.3's legibility
principle applies everywhere in Insights, not just the score itself), share a Monthly Wrapped,
opt into or out of cohort/leaderboard visibility.

### Data flow
Insights is a pure read layer — a view over the Academic Profile, Progress Metrics, and KAIRO
Score already computed elsewhere (Student Intelligence Model §2, §6, §7). It writes nothing new
back into the model except explicit user preferences (leaderboard opt-in/out, report sharing).

### Intelligence Engine interactions
**The KAIRO Score model, confirmed here as final:**
**45% Accuracy (difficulty & recency weighted) + 35% Retention (Reinforced-transition based) +
20% Consistency (engagement-pattern based)** — explicitly not XP, explicitly decoupled from
streaks, explicitly resistant to gaming through volume, guessing, or cramming (Student
Intelligence Model §7.2–7.4). Insights is where this model becomes visible and explainable to
the student, never where it's computed.

### Edge cases
New student with insufficient data → Insights shows the same "your picture is building" framing
as the Home Dashboard's empty state (Home Dashboard §7), never a zeroed-out chart.
Score drop after a difficult week → the plain-language breakdown proactively explains *why* in
neutral, non-alarming terms (per KAIRO Score §7.4's legibility guarantee), rather than leaving
the student to interpret a falling number alone.

### Future scalability
Parent Dashboard (Student Intelligence Model §9) is a filtered read of exactly this layer —
Insights' data model already anticipates that extension.

## 8. PROFILE

### Purpose
Personal identity, goals, and account management — the stable Student Identity layer (Student
Intelligence Model §1) made student-facing and editable.

### Student journey
Open Profile → review/update goals, target university/course, exam year → manage achievements
and badges → adjust account/notification settings.

### Major screens
- **Profile Overview** (name, target course/university, exam countdown context, achievement
  highlights)
- **Goals Screen** (target score, subject combination, study time preferences — feeds directly
  into Student Intelligence Model §1's declared fields)
- **Achievements & Badges** (full, permanent record — distinct from Insights' recent-activity
  framing)
- **Account Settings** (notification timing/preferences, data/offline settings, support)

### User interactions
Edit goals (target score, target university/course), update subject combination, manage
notification timing preferences, review full badge history, reach support.

### Data flow
Profile edits write directly to Student Intelligence Model §1 (Student Identity) — this is the
one layer of the model that is *declared*, not inferred, and Profile is its sole editable
surface.

### Intelligence Engine interactions
Changing a goal (e.g., target course) triggers the DDE's re-scoping behavior already specified
(DDE §13 — "The student changes goals") — Content Map subtree and countdown context update from
the next session onward, with no retroactive rewriting of past data.

### Edge cases
Student changes exam year mid-journey (repeat candidate scenario) → historical Knowledge Map is
preserved and treated as valuable signal, not discarded, exactly as the Learning Engine's
multi-year scalability principle already specifies (Learning Engine §12).

### Future scalability
The dormant Parent/guardian contact field (Student Intelligence Model §1) has its natural UI
home here, ready for the future Parent Dashboard extension without redesign.

## 9. THE INTERCONNECTION PRINCIPLE

Every section above is a different door into the same house. None of them are silos:

```
Practice   → updates Review's mistake/Fading queues
Review     → updates Learn's concept-priority surfacing
Learn      → updates confidence_score, which feeds the KAIRO Score
CBT Mode   → updates weakness detection across the whole Knowledge Map
Challenges → update Insights (lightly) and the misconception library
Insights   → recommends what Practice should prioritize next
Profile    → re-scopes what the entire Intelligence Engine considers relevant
```

This mirrors the Student Intelligence Model's own circular loop (Student Intelligence Model
§8) — every section is a *consumer and contributor* to one continuously-updating model, never a
separately maintained parallel dataset. A student may experience KAIRO as eight distinct
destinations. The Intelligence Engine never sees eight destinations — it sees one continuous
stream of signal about one student, regardless of which door it came through.

## FINAL OUTPUT — WHY INTENT-BASED ARCHITECTURE IS THE RIGHT ARCHITECTURE

A single forced learning path optimizes for the Intelligence Engine's convenience, not the
student's reality. Real students do not open an app with one motive every day — some days they
want the comfort of structured practice, some days they want the adrenaline of a timed mock,
some days they want a two-minute Challenge shared by a friend on WhatsApp, some days they simply
want one stubborn concept explained clearly. A product that only offers one of these experiences
forces the student to either abandon their actual intent or abandon the app.

By organising KAIRO around eight clear intents — all backed by one unified Intelligence Engine —
the product gets to say yes to whichever door the student walks through today, while quietly
ensuring that whichever door it was, the system gets smarter about that student. This is the
same principle that governs the Daily Decision Engine at the session level, now applied at the
level of the entire product: **remove the decision, not just answer it quickly** — and let every
path, however different it feels, lead back to the same honest, continuously-updating
understanding of the student.

**Think Smart. Perform Elite.**
